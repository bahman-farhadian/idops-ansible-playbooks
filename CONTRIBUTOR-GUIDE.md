# Contributor Guide

This is the single contributor standard for the entire repository.

## Purpose

Use one consistent Ansible project pattern across all domain directories (`aa-*`, `ab-*`, ...).
Use `playbook-template/` as the default scaffold for new implementation projects.

## Scope

These rules apply to every active implementation project inside this
repository: the domain directories (`aa-*`, `ab-*`, ...) and
`playbook-template/`.

`old_playbooks/` held superseded work kept temporarily for reference while its
projects were migrated. It has been removed now that every project it held has
an adopted replacement in a domain directory; see each domain's README for the
migration note. New work belongs in a domain directory, scaffolded from
`playbook-template/`, never in a legacy holding directory.

## Required Standards

1. Exactly one top-level playbook entrypoint: `playbook.yml`.
2. Do not create multiple top-level workflow playbooks.
3. Put workflow logic in `tasks/*.yml` and include from `playbook.yml`.
4. Keep user-editable runtime settings in `vars/` with documented defaults.
5. Use `venv/` as local Python environment path when needed (not `.venv`),
   created with `python3 -m venv --prompt idops-ansible-project venv` (the
   root `make venv` does this) so the shell prompt identifies which project
   is active rather than showing the generic `(venv)`.
6. Expose user workflows through `Makefile` targets.
7. Every implementation `Makefile` must include `make ping`.
8. Every user-facing Make target must appear in `make help`.
9. Keep `help` as default Make target.
10. Never commit macOS `.DS_Store` files.
11. Never commit Python virtual environment contents. `venv/` and `.venv/` are local-only paths.
12. Keep committed settings blank. Every top-level key in a tracked `vars/`
    file is a type-appropriate placeholder, not a working value — real
    hostnames, SSH keys, local storage paths, the hosts someone deploys to or
    tests against never belong in a tracked file, and neither does any other
    real default. The one exception is a variable Ansible must resolve before
    the settings-file guard (Standard 14) can run, such as a templated
    play-level `hosts:` — leave that one at its real value with a comment
    explaining why.
13. Every project exposes a machine-local override file,
    `vars/settings.local.yml`, loaded last so it wins, generated by
    `make settings`. This is the only place real values live, and the only
    standard way to point a project at a real environment; editing tracked
    settings files to do it is not.
14. Every implementation `Makefile` must include `make settings`, every
    `playbook.yml` must load the override file in every play as a plain,
    required `vars_files` entry (never the "first found" nested-list form),
    and the first play must fail immediately with a clear message if the file
    does not exist — a missing `vars_files` entry is silently skipped by
    Ansible rather than erroring, so this guard is not optional.
15. Machine-local settings are never committed. `*.local.yml` and both
    secrets-file spellings (`local-secrets.yml`, `local_secrets.yml`) are
    gitignored, and `make check-local` at the repository root fails if one
    is ever tracked or staged. Run it before pushing.
16. No AI attribution in any commit, anywhere: no `Co-authored-by:` line
    naming an assistant or model, no `Generated by ...`, no equivalent marker
    in a commit message, author field, or committer field. Every commit
    reads as authored by a person. If a commit carrying one is found before
    it is pushed, fix it (amend if it is the tip and unpushed, otherwise
    rebase) rather than adding a new commit on top of it — history should not
    document a mistake that could still be removed cleanly.
17. Every setting's trailing comment in a tracked `vars/` file ends with
    either `Values: ...` (an enum or boolean, listing every valid value) or
    `Example: ...` (an open-ended value, showing what a real one looks
    like) — a description of what a key does is not enough on its own.
    Within any run of consecutive `key: value` lines with no blank line,
    banner, or block between them, align every trailing comment to the same
    column. A key blanked to `[]` or `{}` additionally carries a worked
    example immediately below it (no blank line in between), introduced by
    the exact line `# Example (was the live default; see local settings for
    real values):` — that exact sentinel is what lets `make settings` find
    it and copy it along with the key. `vars/settings.local.yml`, generated
    by `make settings`, carries all of this: every setting's own comment and
    worked example travels with it, so an operator can tell what to type
    without a second file open. It is still generated, not hand-maintained -
    edit the tracked file, not the copy of its comment here, if the
    documentation itself is wrong.
18. A tracked inventory file (`host.yml`, `inventory.ini`) is never
    hand-edited with a real host's address, user, or password. It stays a
    static placeholder — an empty group, at most a `local`/`localhost` entry
    for the play that resolves real hosts — and the first play adds real
    targets to it dynamically with `add_host`, sourced from a list var
    (`kvm_hypervisors`, `debian_hardening_targets`, ...) that lives in
    `vars/settings.local.yml` like any other real value. See "Declaring Real
    Hosts Without Tracking Them" below. If a project's design cannot avoid a
    raw `ansible` ad-hoc command against a static group (rather than
    `ansible-playbook` against the dynamic one), route it through the
    playbook as another action instead of a second, parallel inventory path.

## Best-Practice Project Structure

Minimum structure for each implementation project:

- `playbook.yml`
- `tasks/`
- `vars/`
- `inventory.*`
- `ansible.cfg`
- `requirements.txt`
- `Makefile`
- `README.md`

Optional but recommended:

- `venv/` (local environment path, ignored by Git and recreated with `make venv`)
- `wheelhouse/` (local wheel cache directory)
- `docs/` (operator runbooks and architecture notes)

Reference tree:

```text
<project>/
  playbook.yml
  tasks/
  vars/
  inventory.ini
  ansible.cfg
  requirements.txt
  Makefile
  README.md
  wheelhouse/
    .gitkeep
```

Do not add placeholder files under `venv/`. The full directory is ignored because
virtual environments contain path-sensitive scripts and interpreter references.

## Naming Rules

1. Use `playbook.yml` for the single top-level playbook entrypoint.
2. Use descriptive action names for task files, for example:
   - `tasks/provision.yml`
   - `tasks/cleanup.yml`
   - `tasks/ping.yml`
3. Use descriptive variable file names under `vars/`.
   - Prefer domain-scoped names, for example `vars/hypervisor-platform.yml`.
   - Once a settings file covers several unrelated topics, split it into
     numbered per-topic files that state defaults before the thing that uses
     them, as `ac-vm-provisioning/kvm-vm-provisioning/vars/` does:
     `01-hypervisors.yml`, `02-vm-defaults.yml`, ... `06-instances.yml`.
   - Reserve `*.local.yml` for machine-local overrides. It is gitignored.
4. Use kebab-case for directory names and repository domains.

## Machine-Local Settings

Tracked settings files are documentation, not configuration: someone reading
`vars/` should see what a setting means, not a working value — and never the
hostnames, IPs, or passwords of whoever committed last. Every tracked setting
is a type-appropriate blank placeholder. Real values live in exactly one
place: `vars/settings.local.yml`, an override file that git never sees. A
project in this repo will refuse to run at all without one.

### How It Works

1. Every top-level key in a project's tracked vars files is blank — `""` for
   strings, `~` for numbers/booleans, `[]`/`{}` for lists/mappings. A worked
   example that used to be the live value is kept as a comment directly below
   its key, so the shape of a real value is still documented.
2. `vars_files` loads top to bottom, and the last definition of a key wins.
   `vars/settings.local.yml` is loaded last, as a plain, required entry — not
   the "first found" nested-list form, because that would make it optional.
3. Ansible silently skips a missing `vars_files` entry instead of erroring, so
   a missing settings file would otherwise leave every setting blank with no
   warning. The first play in every project therefore starts with an explicit
   guard that stops the whole run with a clear message instead:

```yaml
  vars_files:
    - vars/01-hypervisors.yml
    - vars/02-vm-defaults.yml
    # Every tracked value above is blank; this is the only source of real
    # values, and it is required - see the fail task below.
    - vars/settings.local.yml

  tasks:
    - name: Check for the machine-specific settings file
      ansible.builtin.stat:
        path: "{{ playbook_dir }}/vars/settings.local.yml"
      register: local_settings_file
      changed_when: false

    - name: Fail when settings.local.yml is missing
      ansible.builtin.fail:
        msg: >-
          vars/settings.local.yml is required and was not found. Every
          tracked setting is a blank placeholder; this file is the only
          place real values live. Generate a starting point with:
          make settings
      when: not local_settings_file.stat.exists
```

**One narrow exception:** a variable Ansible must resolve before that guard
task can ever run — most commonly a play-level `hosts:` templated from a
var — cannot be blanked, because a blank there breaks `make check`/`make
lint` and every run, guard included, with a confusing parser error instead of
the intended message. Leave that one variable at its real, working value, and
say why in a comment next to it. All three projects in this repository avoid
needing this today: `hosts:` is always a literal group name (`hypervisor`,
`hardening_targets`, `managed_target`), and real hosts are added to that
group dynamically at runtime from a list var (`kvm_hypervisors`,
`debian_hardening_targets`, ...) that lives entirely in
`vars/settings.local.yml` — see "Declaring Real Hosts Without Tracking Them"
below. Reach for this exception only if a future project's design genuinely
cannot follow that pattern.

### Adding It To A Project

1. Blank every top-level setting in the project's tracked vars file(s) to a
   type-appropriate placeholder, keeping any multi-line worked example as a
   comment below its key (see "How It Works" above, and the one exception).
2. Append `vars/settings.local.yml` — a plain, required entry, not a
   nested-list fallback — to every play's `vars_files`.
3. Add the `stat` + `fail` guard shown above as the first two tasks of the
   first play.
4. Add the reporting step Rules For Operators requires: an `include_vars`
   loading `vars/settings.local.yml` under its own name, then a `debug` task
   printing how many keys it supplies and their names, both gated on the
   same `stat` result, right after the guard. kvm-vm-provisioning's
   "Load the machine-specific override file for reporting" /
   "Report which settings come from the override file" tasks are the
   template - copy them, renaming the fact and the tracked file it names.
5. Add a `settings` target calling
   `$(PROJECT_ROOT)/scripts/generate-local-settings.py`, and list it in
   `make help`.
6. Add `settings-clean`, `settings-clean-force` and `settings-clean-force-all`
   targets calling `$(PROJECT_ROOT)/scripts/clean-local-settings.py`
   (`--vars-dir vars`, then `--remove-disposable`, then `--remove-active`
   respectively), and list all three in `make help`.

`make settings` writes `vars/settings.local.yml` containing every setting the
project exposes, grouped by source file, each with its own inline comment
and (for a key blanked to `[]` or `{}`) its worked example carried along -
copied from the tracked file, not retyped, so it cannot say something the
tracked file does not. Every value is live, at its current tracked default
(now a blank placeholder), ready to edit in place — nothing needs to be
uncommented before it takes effect. Filling in real values here is what
makes the project able to run at all.

Because every value is live, a key this file mentions stops following the
tracked default the moment it is generated: the local value always wins even
if it is, for now, identical to the default. If that default later changes
upstream, this file will not follow unless the operator updates it too.
Comment out or delete a line to let that key track the default again.

### Running It Again Is Safe

`make settings` is idempotent and additive: run against an existing file, it
adds only the settings that are new upstream and not yet mentioned anywhere in
the file, live or commented, appended in a dated section, live at their
current tracked value the same as a fresh file. A line that is already there,
including one the operator has since edited or commented back out, is never
touched. Nothing new to add means the file is not written at all, so running
it twice in a row with no upstream change leaves it byte-for-byte identical.
This is what makes it safe to run again after a project adds a setting: the
operator's existing configuration cannot be damaged by picking up what is new.

`FORCE=1` is the one way to discard local edits: it replaces the file from a
clean template, after copying the previous one to `<file>.bak` first, since
the file itself is not otherwise backed up.

### Looking Up A Field You Have Not Used Yet

The sync in `make settings` only tracks whether a top-level key exists at all,
and never touches a line already present - so a key that is a list of
mappings, such as `kvm_hypervisors` or `kvm_instance_definitions`, keeps the
worked example comment it was generated with even after being customised,
frozen at whatever the tracked file looked like that day. If the tracked
file's example later grows a field this comment does not show (a new
per-host key, say), `vars/settings.local.yml` will not pick that up on its
own. When that happens, read the tracked vars file the key comes from — it
is the source of truth for what fields currently exist. This project tried
generating a second, disposable copy of that same information on demand
(`make settings-reference`); it worked, but it was a command and a mental
model to explain for something a single file already answered. Removed for
that reason — see "Keep This Simple" below.

### Cleaning Up: `make settings-clean`

Two tiers, on purpose:

- `make settings-clean` lists what exists; removes nothing.
- `make settings-clean-force` removes only the disposable tier — any
  `*.local.yml.bak` left by a `FORCE=1` run. These regenerate on demand, so
  nothing here can be lost, and `vars/settings.local.yml` itself is never
  touched.
- `make settings-clean-force-all` additionally removes
  `vars/settings.local.yml`. This is not reversible: it holds real, hand-built
  configuration that git does not back up. Back up anything worth keeping
  before running it.

The split exists because "clean up this project's local files" should never
be one command away from deleting configuration that took real effort to
build. Reaching the destructive tier requires naming it explicitly.

### Rules For Operators

- The project will not run without `vars/settings.local.yml`. There is no
  tracked fallback; every tracked value is a blank placeholder, and the first
  play fails immediately with a clear message if the file is missing.
- Every value is live the moment it is generated. Comment out or delete a line
  to release that key back to following the tracked default; leave it as-is
  and it stays pinned even after the tracked default changes.
- Overriding replaces the whole value; it does not merge. A list here must
  list every entry that should exist, because the tracked list is replaced.
- Once a key lives in the local file, edit it there. The same key in a tracked
  file is ignored from then on.
- `*.local.yml` is gitignored, so git does not back it up either. Keep your own
  copy of anything you cannot recreate.

A project should report which keys the local file supplies at the start of a
run, so a tracked-file edit that appears to do nothing is explained where it
happens rather than found by comparing two files.

### Keeping Local Settings Out Of Git

Two layers, because an ignore rule alone is not a guarantee — `git add -f`
defeats it, and a reviewer may not notice:

1. `.gitignore` covers `*.local.yml`, `*.local.yml.bak` and both secrets-file
   spellings (`local-secrets.yml`, `local_secrets.yml`) repository-wide.
2. `make check-local` at the repository root fails if any such file is tracked
   or staged, naming the file and the command that removes it. Run it before a
   push, or wire it into CI.

```bash
make check-local
# OK: no machine-local settings file is tracked or staged.
```

Because git does not track these files, it does not back them up either.
`make settings` can always regenerate the current tracked defaults, but not
the values an operator chose on top of them: keep your own copy of the
override file itself if its contents took real work to build.

### Keep This Simple

This mechanism has already grown once and been cut back once. `make
settings-reference` was removed for exactly the reason above: it solved a
real gap (the full field list of a customised entry going out of sight) by
adding a second generated file, a fourth Makefile target, and a paragraph
explaining how the two files related to each other — more machinery than the
gap was worth, when the tracked vars file already answers the same question.

Before adding a new mode, flag, or target to this mechanism, check whether
the tracked vars files can already answer the question without one. If they
can, point at them instead of generating a copy of them.

### Secrets

Secrets stay separate. `ag-os-baseline-and-hardening/debian-os-hardening` keeps
them in `vars/local-secrets.yml` with a committed `.example` alongside. Use the
local settings file for machine-specific configuration, and a secrets file for
credentials.

`make settings` never reads a project's secrets file (`local-secrets.yml` or
`local_secrets.yml`, either spelling) as a settings source, on purpose: that
file is loaded by its own `include_vars` task, independent of and with higher
precedence than `settings.local.yml`, so copying its keys in here would
duplicate a real secret into a second file and leave a copy that looks
editable but is silently ignored at runtime. If a future project's secrets
file uses a different name, add it to `SKIP` in
`scripts/generate-local-settings.py` before wiring it up.

### Declaring Real Hosts Without Tracking Them

The settings mechanism keeps real values out of tracked `vars/` files. A
tracked inventory file is the same risk in a different shape — `host.yml` or
`inventory.ini` is not gitignored, so a real address, user, or password
hand-edited into it commits as readily as any other tracked file, and
`check-local` cannot catch it because it is not a `*.local.yml`-style file at
all.

All three projects in this repository solve it the same way:

1. The tracked inventory file declares only a static placeholder — an empty
   group (`hosts: {}`) for real targets, plus a `local` group with an
   explicit `localhost` entry for the first play, which always runs against
   `localhost` itself.
2. Real hosts live in a list var (`kvm_hypervisors` in
   `01-hypervisors.yml`, `debian_hardening_targets` in
   `debian-hardening.yml`) - blank in the tracked file, real only in
   `vars/settings.local.yml`, exactly like every other setting.
3. The first play validates that list (at least one entry, valid and unique
   names, sane ports) and adds each entry to the real inventory group with
   `ansible.builtin.add_host`, before the second play ever runs against that
   group.

A project's Makefile should never run a raw `ansible` ad-hoc command against
a project's target group, because ad-hoc commands are not plays and never
run the play that populates that group with `add_host` — they would only see
whatever the static, empty placeholder declares. `debian-os-hardening`'s
`ssh-check` and `runtime-check` targets used to do exactly this, reading
connection details out of the tracked `host.yml` to work around it; they
were rewritten as two more `debian_hardening_action` values
(`tasks/ssh-check.yml`, `tasks/runtime-check.yml`) dispatched through the
same `playbook.yml`, so there is exactly one path that resolves real hosts,
not two.

## What Is `wheelhouse`?

`wheelhouse/` is a local cache directory for Python wheel files downloaded by pip.

Why it exists:

1. Reduces repeated dependency downloads.
2. Helps offline or restricted-network environments.
3. Makes dependency bootstrap more predictable.

Best practice:

1. Do not commit full `venv` binaries.
2. Do not commit any files under `venv/` or `.venv/`.
3. Keep only placeholders in `wheelhouse/` by default.
4. If your team decides to commit wheel artifacts, treat them as managed release artifacts and document that policy in the project README.

## Branching

Committing directly to `main` for every change makes `main` a running log of
in-progress work instead of a record of what is actually done, and gives
nothing to fall back to if a change set turns out to be wrong halfway through.
Work lands on a branch and reaches `main` only once it is coherent and
validated.

### Naming

```
<type>/<short-kebab-description>
```

`<type>` is one of the commit types already used in this repository:
`feat`, `fix`, `chore`, `refactor`, `docs`, `test`, `perf`, `ci`, `build`.
The description is a few kebab-case words, specific enough to identify the
branch in a list without opening it — no ticket numbers, no dates (git
already timestamps every commit), no personal names.

```
feat/kvm-ubuntu-support
fix/kvm-trailing-slash-paths
chore/venv-prompt-rename
docs/branch-naming
```

Scope the description to a domain or project when the change is local to
one, the way commit subjects already do: `feat(kvm-vm-provisioning): ...`
becomes `feat/kvm-<description>`.

### Practice

1. Branch from `main` before starting a change; do not commit new work
   directly on `main`.
2. One branch per coherent change set, matching the "one intent per commit"
   rule below at the branch level. Do not accumulate unrelated work on one
   branch waiting for a good time to split it up.
3. Merge (or fast-forward) into `main` once the change set is complete and
   validated, then delete the branch. A branch that is still useful after
   merging is a sign the change set was not actually finished.
4. Keep branches short-lived. A branch that sits open for a long time drifts
   from `main` and turns an eventual merge into its own investigation.

## Commit Practice

1. Commit after each coherent change set.
2. Keep commit messages short and explicit.
3. Prefer one intent per commit.
